# Video production and interaction inside Claude and ChatGPT

Questions and story discussion belong to the host conversation; custom app surfaces display actual media. Check the deployed harness version before validating a new flow. Local protocol and browser tests do not establish signed-in Claude/ChatGPT behavior or prove that online reference research occurred.

## Two components with one creative context

**Video production** edits and creates the piece: source inspection, narration, scene construction, rendering, assembly, review and export. The host assistant orchestrates these operations through MCP. Editable sources and measured production timing belong to this component; displaying a form or calling a task successful does not prove that the video is correct.

**Experience and alignment** helps the person express what they want and understand what is being made. It chooses useful questions, examples, story proposals and visual updates for the current request. It should identify consequential uncertainty about audience, emphasis, style or story, rather than asking for approval at every production stage. The user should mainly see their material and the evolving video, accompanied by concise conversation.

The shared contract is persisted creative context with explicit provenance and a revision. Assistant assumptions, proposed story beats and submitted user preferences remain distinguishable. Production results return current preferences so the next affected edit can adopt a change while retaining compatible work. An unanswered question is never approval. Whether dependent work should wait depends on the request's intake stage, selected involvement mode and any real blocker.

## Version-1 request flow

Every new version-1 request starts with an explicit involvement choice: **Hands off**, **Key moments**, or **Hands on**. Ask this first, before content questions or substantial production. A recommended option is not a selected mode. Next ask only for missing high-level output basics, such as duration and destination; use the information already in the request and do not mix content or style questions into that step. Continue editing the same request without repeatedly asking its mode. Legacy projects without version-1 intake retain their existing explicit preference or a labeled key-moments default.

| Selected mode | Experience after output basics |
| --- | --- |
| Hands off | Make the creative decisions and complete the requested production without optional questions, story/preview cards or routine progress updates. Deliver the final playable video and download. Explain a real missing input, unavailable service or allowance shortfall when it requires user involvement. |
| Key moments | Preserve selective collaboration: a few consequential choices or useful drafts, with reversible independent work continuing where appropriate. Do not invent a questionnaire for a precise edit or supplied script. |
| Hands on | After output basics, consult the maintained source registry and research 2–3 real visual/video references with host search/fetch and the isolated reference browser when needed. Let the user choose or combine traits, refine the search from dislikes, then create a short representative snippet for explicit review before the rest. Wait for dependent decisions; cheap independent inspection can continue. |

The maintained source registry, `video_use_mcp/pilot/reference_sources.json`, supplies approved discovery collections, categories, search/inspection notes, research verification and access limits. Read `reference_sources` in `start_video` or capabilities before searching. Its initial eleven primary sources are a starting collection, not exhaustive coverage: podcasts and document-to-video lack dedicated collections; social clips and personal montages have weaker coverage. Reserve mentions in the research are not automatically approved sources. If no collection fits, explain the gap and ask for a user reference or explicit delegation to a described direction. General open-web discovery is not enabled by a coverage gap. The curator handoff is [the reference-source research prompt](prompts/reference-source-research.txt).

The registry stores search locations and access knowledge, not preinspected media to recommend repeatedly. The assistant must search and inspect actual references in real time for each query. Historical seeds or example pairs are not current recommendations. It derives a query-specific visual search intent from the audience, source material, requested treatment and constraints, then routes adaptively through useful collections and filters. Batch 2–3 independent targeted queries when the host supports parallel search; scan inexpensive titles, descriptions and actually available thumbnails before inspecting only 2–3 promising finalists. Actual playback of a short representative excerpt can establish a motion trait; do not deeply inspect every candidate or repeatedly retry inaccessible playback. Stop at distinct useful choices and deepen inspection only when feedback needs it. A roughly 20–40 second first shortlist is an aspiration when access permits, not a guarantee or backend deadline. Cache navigation/media locations, not fixed candidate choices.

`browse_video_references(project_id, request_id, operations, budget_seconds=30)` supplies a Browser Harness browser for JavaScript galleries, page controls and media that inexpensive host search/direct fetch cannot inspect. It is available during reference intake, before render authorization. The host Claude or ChatGPT assistant chooses queries, actions, candidates and interpretations. The browser executes bounded operations in a dedicated isolated container without another model or model API key; it does not conduct an autonomous search after the host stops.

Each batch accepts up to six operations and a 5–45 second action budget: `search`, `open`, `read`, `click`, `fill`, `press`, `scroll`, `screenshot`, `sample_video` and `close`; cold startup can add time. Search takes a query and 1–3 approved source IDs; host search remains preferable when available. Navigation starts at curated roots or an explicit user-supplied URL, then follows evidenced creator/media links. Returned text, links and AX nodes guide the next operation; use observed `node_id` targets for clicks and fills. One attached tab belongs to one browser per project, with at most two browsers globally, a 60-second idle lifetime and a 180-second absolute lifetime. Browser time uses the existing compute allowance. Close after research. It does not inherit host cookies, accept account passwords, import reference media or record full browsing sessions.

Browser results include inline captures and retained evidence IDs; save relevant `evidence_ids` on references through `record_video_references`. `read_video_reference_evidence(project_id, evidence_id)` can return retained images for inspection. The assistant must actually inspect those images before reporting visual traits. A successful capture, saved evidence ID or navigation trace is not proof of that inspection. `sample_video` captures up to three timestamped frames: they support visible states at those moments, not continuous motion, transition quality, pacing or audio. Record this as image-level evidence with timestamps and limitations, not watched-video evidence. Actual playback requires a tool that exposes it to the assistant and an honest account of what was observed.

Registry order and category examples are hints, not a required first-two-sites algorithm. Compare brief fit, useful design traits, inspection evidence and feasible adaptation to select 2–3 meaningfully distinct approaches. No arbitrary pool quota or numerical score substitutes for that judgment. Each offer's `search` record saves `search_intent`, `search_queries`, `candidates`, `selection_reason` and `coverage_limitations`. Candidates contain the reference, evidence note, fit, limitations and recommendation/reserve/rejection disposition; the 1–12 record bound is not a minimum pool or required rejection quota. Technical or factual subject research remains separate from visual inspiration; popularity alone establishes neither fit nor quality.

Present references through normal chat, source links, native link previews or images when supported, without a custom form. The source research established page/index access, not playback. A registry verification level is not proof that this run inspected the work. Reference `inspection` is `metadata`, `page`, `image` or `video`: `metadata` records index/title-only screening, not an opened page or visual inspection. Partially inspected finalists need explicit limitations, not a claim of visual verification. Attribute page claims; actually viewed images can support visible palette, composition or type, while an image URL cannot. Still images cannot establish motion, pacing or sound; an animated image proves motion only when its sequence was actually observed. Claim clip playback only when a capable tool supplied that evidence. Be explicit about limits and let the user watch an accessible link when playback is unavailable. Optional `search.elapsed_seconds` reports measured research time only; omit it when unavailable. Assistant-reported evidence and saved evaluation reasons are not automatic semantic validation or proof of artistic quality.

Let the user choose or combine specific design traits. On rejection, identify which attributes need changing—pace, medium, texture, palette, composition, type or mood—and ask one targeted question only when unclear. Retain accepted traits, dislikes and excluded references while changing the relevant collection, filter or query. “Too corporate” is not a deterministic instruction to use one website or aesthetic. Use `record_video_references` to save offered sources, selections, refinements or explicit delegation, with inspection evidence, selected traits and the user's actual words; use those traits in the sample's composition, type, motion and rhythm. Choosing inspiration does not import its media or approve an unseen film.

An explicit user reference, exact edit or request to skip search can delegate this stage when the user's words and direction are recorded. If host search and browser access cannot provide suitable evidence, say so and ask for a reference or permission to use a described direction. Do not fabricate research, silently fall back to cached samples, or interpret inactivity as acceptance. Hands off and Key moments retain their existing behavior.

Hands-on involvement is a request for useful creative checkpoints, not approval of every terminal command. The agent still chooses the questions that fit the piece; there is no fixed topic questionnaire, compulsory aesthetic or required scene count. A known answer need not be asked again. Once the requested early decisions are settled, continue toward the complete reviewed result and apply later feedback to affected work.

`intake.py` owns the versioned setup and initial-snippet review state. `experience.py` derives conversation guidance from that state, actual task results and saved input: a meaningful visual, changed preferences, failure, cancellation, completion or a real blocker. Experience reads do not mutate state or claim a question was displayed or answered. The repeat key helps avoid repeated updates, while the persisted intake state determines which decisions remain outstanding. These choices are request-specific; they do not establish an account-wide learned preference or authorize extra spending.

Do not replace conversation with tool status text or show empty workspace containers as progress. In hands-on mode, display the representative excerpt before investing in all remaining scenes. In hands-off mode, an internal excerpt can still test production quality without becoming a user-facing update.

`allowance.py` supplies narration capacity in relevant capability and story results. Discuss it only when requested speech faces a material limit, not during the opening mode question. The saved story can compare its proposed script against remaining characters. The report and atomic admission share the same database limit definition. Committed and unsettled reserved allowance both count; available capacity is the smaller of personal and shared remaining capacity. A read does not reserve capacity, call the speech provider or measure provider charges. Unknown capacity must remain unknown. A known shortfall merits an early focused choice while useful independent sketches can continue; it must not silently remove requested voiceover.

Native Claude question dialogs, research buttons, Docs and third-party app libraries are host or separate-connector features. Their appearance in another assistant's inventory does not make them callable APIs of this MCP. Project-specific direction galleries, voice auditions, visual storyboard thumbnails/reordering, A/B versions and delivery packs remain distinct implementation work; the current controls do not imply these features are complete.

## Host surfaces and boundaries

The same MCP tools and saved state serve both hosts. Host-specific evidence below does not establish identical display or continuation behavior in ChatGPT; negotiate capabilities and verify the account flow separately.

Verified against primary documentation on 2026-10-01. MCP Apps provides a sandboxed HTML/JavaScript interface, not a fixed catalog of widgets. We can build buttons, forms, sliders, selectable cards, image comparisons, a storyboard, video/audio controls, waveforms and a drawing canvas within that interface. Their editing behavior still needs server-side implementation; displaying a control does not add a rendering capability. See the [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview) and [official examples](https://github.com/modelcontextprotocol/ext-apps#examples).

| Surface or behavior | Evidence and implementation rule |
| --- | --- |
| Inline card | Supported in Claude for useful visuals and playable drafts. Questions use a native question tool if available, otherwise normal chat; do not turn setup into a custom form. |
| Fullscreen view | Supported in Claude, with the conversation input still available. Offer expansion only when `getHostContext().availableDisplayModes` includes `fullscreen`; use `requestDisplayMode`, then respect the returned mode. |
| Picture in picture | Defined by the MCP Apps protocol, but not documented as a Claude surface in the current help article. Do not promise or require it. Enable only if a host advertises it and it is tested there. |
| Video, images and audio | Ordinary web media inside the app; use authenticated or short-lived asset URLs covered by the declared resource domains. Our current app already displays images and playable MP4s. |
| Buttons, forms, choices, sliders, drag/reorder | Implementable with HTML/JavaScript. Local preview changes can happen immediately; persistent edits need an authenticated server tool. These are our controls, not native Claude question dialogs. |
| Live updates in an existing card | Supported through app-only tool calls. This can refresh the visual without a model turn for each refresh. Calls still create backend traffic; no claim is made about exemption from host usage limits. |
| Streaming partial tool input | Optional protocol feature. Useful for noncritical previews where supported; incomplete input must not start production work. Not a reliable substitute for a completed visual. |

Claude documents [inline and fullscreen connectors, permissions and iframe security](https://support.claude.com/en/articles/13454812-use-interactive-connectors-in-claude). The SDK documents [fullscreen negotiation, app-only tools, polling and partial-input handling](https://apps.extensions.modelcontextprotocol.io/api/documents/Patterns.html). The [protocol specification](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx) defines optional display modes and lifecycle behavior. Host capabilities must be checked at runtime rather than inferred from the host name.

## Context updates do not keep a model running

`updateModelContext` supplies state for a future model turn. It does not trigger an immediate response, and subsequent updates replace earlier context from that view. Send a compact current state rather than assuming incremental updates will accumulate.

`sendMessage` submits a message with the `user` role and may trigger a follow-up. The host can reject it or require consent. Use it after an explicit user action such as **Apply changes** or **Send suggestion**; never manufacture user messages from a timer or completed render. A successful save and a sent chat turn are separate outcomes. Even a successful host response may only prepare a composer draft: use short human text, retain IDs/revisions/JSON in background context, and say that the prepared reply may need sending. See the SDK's [updateModelContext](https://apps.extensions.modelcontextprotocol.io/api/classes/app.App.html#updateModelContext) and [sendMessage](https://apps.extensions.modelcontextprotocol.io/api/classes/app.App.html#sendMessage) contracts.

The server remains authoritative: save preferences first, return the current creative revision in subsequent tool results, and let the next production step adopt the change. Show a truthful fallback if the host cannot deliver a follow-up. Neither API guarantees interruption of current reasoning, endless generation, or bypassing Claude's turn/tool/usage limits. App code also cannot control Claude's surrounding attribution, tool approvals or reasoning display.

## Implemented interaction catalog

`video_use_capabilities().interaction` now lists the available interaction types. The assistant selects the ones that fit the request; the catalog is not a workflow checklist or a promise that the host has already displayed them.

| When it helps | MCP tool / interface | Current behavior |
| --- | --- | --- |
| Required setup or a consequential unresolved choice | `start_video`, `show_video_brief` | Returns a stable question for the host to ask natively when possible, otherwise in chat; no custom form. Present the question already returned by `start_video` rather than registering it again. Mode comes first, missing basics second, then request-specific decisions. |
| Online references establish hands-on direction | Host search/fetch, `browse_video_references`, `read_video_reference_evidence` and project reference context | Consult curated sources, inspect query-specific examples, preserve evidence IDs/source URLs and save chosen traits/dislikes. The isolated browser supports interactive pages and sampled media; native chat previews/images are optional host features. Cached clips are not an automatic substitute. |
| Cached examples help a Key moments decision | `show_video_choices` | Optional known technique samples, explicitly labeled as cached references. Hands off skips this gallery; it does not replace hands-on online research. |
| The story needs a saved plan | `show_video_story` or `plan_video` | Persists the proposed beats and script internally. Discuss a short outline only when useful; no custom editor or technical EDL dump. Proposed durations are not measured timings. |
| A useful image, excerpt, complete draft or final export exists | `show_video_preview` | Displays actual media with download and **Edit this moment**. **Larger labels**, **Faster pace** and **Change the look** prefill an editable suggestion; only an explicit submission saves or sends it. The existing player can refresh newer media without another assistant display call; active playback and unsent feedback defer replacement. Fullscreen is offered only when the host advertises it. |
| A hands-on user has seen the short sample | `show_video_checkpoint` | Returns a conversational **Continue with this** or **Refine the sample** question bound to that video and creative revision, without a second app card. Remaining production waits for the explicit answer; internal QA is not user acceptance. |
| Material is missing | In-chat source upload | Transfers explicitly selected files into the project. A connector elsewhere in the host does not automatically grant this MCP access to its private files. |

Save actual conversational answers with `record_video_answers`; preserve freeform content without inventing option IDs. The app-only `save_video_widget` remains for previously opened legacy editors, not the primary flow. Waveform editing and timeline trimming are not implemented controls.

Distinguish required setup and requested hands-on decisions from optional suggestions. Wait for the former before dependent work; the latter should not turn every production step into an approval stage. Persist optional feedback without making every small interaction restart the model. Displaying a form is not proof that the host kept its model turn running while waiting for an answer.

Media task results use conditional `preview_delivery.open_if_missing` guidance rather than an unconditional display command. The assistant should reuse an existing working player in the same conversation. The server cannot infer a chat's visible cards from account-level refresh traffic, and one iframe cannot remove earlier host-owned cards; this guidance reduces duplicate calls without pretending to enforce host layout.

## Persistence, continuation and code ownership

`video_use_mcp/pilot/widgets.py` validates and persists brief/story proposals and explicit user submissions. `creative_state.py` serializes edits. Widget revisions are distinct from creative revisions: replaced or stale editors and conflicting request-ID retries are rejected; identical retries do not apply the edit twice. Saves preserve unrelated creative fields. Story edits carry `user_edit` provenance, while displayed assistant proposals remain `assistant_plan`.

`ui/app.js` and `ui/template.html` render media, optional cached references, source controls and legacy editors. Unsent edits survive failed saves; a newer result does not silently erase them. After a confirmed submission, the app sends compact authoritative context through `updateModelContext` where supported, then attempts `sendMessage` from that explicit user action. A retry confirmed after newer edits updates context without replaying the old instruction. The UI distinguishes a saved change from a prepared chat reply and explains how to continue without claiming the host sent it.

`server.py` registers the tools and exposes the interaction catalog; `workflow.py` supplies request-sensitive guidance. `intake.py` tracks explicit mode, output basics and early snippet review separately from rendering. `experience.py` translates that state and actual outcomes into the next useful conversation. `cards.py` returns fresh creative context with production results and declares the app resource and permitted domains. App-only visibility reduces assistant-facing tool clutter; owner authorization and validated saves still enforce access. These are implemented MCP controls, not a claim that native Claude or ChatGPT question dialogs are callable. No widget can remove the host's approval prompts, guarantee immediate interruption, or keep model generation running after a host limit.

## Recent execution evidence

The local `test_experience_intake.py` cases follow the new request forward through
mode, missing basics, tailored decisions, snippet feedback and final delivery.
They also check that hands-off drafts remain internal, key moments stays selective,
real blockers surface in every mode, and reads do not manufacture approval. These
are state/behavior checks using the intake helper, with no narration or rendering;
they do not prove how a signed-in chat host schedules its next turn.

These findings separate production defects from interaction problems. Times are UTC on 2026-10-01; they describe the observed run, not the state after a later deployment or allowance change.
